# Phase 1: ロスト時の位置ホールド（仕様）

## 目的

Lighthouse の純正ドライバが出力したポーズを vrserver に渡す直前で補正し、トラッキングロスト時の
「吹っ飛び」「瞬間移動」をなくす。追跡が正常なときは、純正の出力を **一切変えずにそのまま** 渡す。

## Phase 0 で分かっていること（根拠: [phase0.md](phase0.md)）

| パターン | 起きること | 例 |
|---|---|---|
| A. 光学ロストが 2 秒以上 | 約 250ms で `Calibrating_OutOfRange`（`poseIsValid` は true のまま）→ 2 秒でリセット（`poseIsValid=false` を 1 回送ったあと更新停止）→ 再開。再開時に BS 1 台から誤った位置で始まると、静止していても 0.3〜0.5m/s で流れ続ける | E2 で最大 85cm、E4 で腰が 6〜8 秒ロスト |
| B. リセットに至らない短いロスト | `Calibrating_OutOfRange` の間に IMU 推測のずれが溜まり、光学が戻った瞬間に段差が出る | E4 のあぐら・横向きで 10〜44cm の瞬間移動 |
| C. 衝撃による即時リセット | `unlikely gravity` で即座に `poseIsValid=false`、0.1〜0.3 秒更新停止、再開時に段差 | E5 の clap で最大 5cm 程度 |

検出に使える信号:

| 信号 | 光学ロストからの遅れ | 確実さ |
|---|---|---|
| `result != Running_OK` または `poseIsValid=false` | 約 250ms | 確実（誤検出なし） |
| 更新リズムの変化（直近 50ms に 1ms 未満の更新間隔がない） | 約 70〜135ms | 誤検出 0〜0.36%（一部のセンサーしか見えない置き方のとき） |
| ポーズ更新の停止 | リセット時（2 秒後 / 衝撃時は即時） | 確実 |

10cm を超える段差 25 件のうち、21 件は「`Calibrating_OutOfRange` から戻った瞬間〜0.4 秒以内」、4 件はそれ以降（0.5〜12 秒後）の正常状態の中で起きた。

## 全体構成

```
lighthouse ──TrackedDevicePoseUpdated──▶ [フック] ──▶ TrackingFilter (デバイスごと) ──▶ vrserver
                                                   ▲
                               エミッタ スレッド ───┘ （更新が止まっている間、保持中のポーズを送る）
```

| 要素 | 内容 |
|---|---|
| `filter/`（新規・静的ライブラリ） | `TrackingFilter`: 1 デバイス分の状態機械。OpenVR の実行時機能に依存しない（`DriverPose_t` の型だけ使う）。ドライバとリプレイツールで同じコードを使う |
| ドライバ | フック内で入力ポーズを `TrackingFilter` に通し、出力ポーズを元の関数に渡す。エミッタスレッドを追加 |
| `tools/ots-replay`（新規） | `.otsrec` を読み、フィルタを通した結果を出力する。Phase 0 の記録でパラメータを調整・回帰テストする |
| 記録 | 入力ポーズに加えて、出力ポーズとフィルタの状態遷移も記録する（新しい記録タイプ） |

## 状態機械（デバイスごと）

| 状態 | 意味 | 出力 |
|---|---|---|
| `TRACKING` | 正常 | 入力をそのまま（ビット単位で同一）。段差リミッタが働いている間だけ位置を補正 |
| `SUSPECT` | 更新リズムから光学ロストの疑い（`result` はまだ OK）。**既定では無効**（リプレイ結果を参照） | 位置を保持、回転は入力のまま |
| `HOLD` | ロスト確定 | 位置を保持、回転は入力のまま（入力が止まったら最後の回転で固定） |
| `PROBATION` | 入力は OK に戻ったが、まだ信用しない期間 | `HOLD` と同じ |
| `BLEND` | 保持位置から入力位置へ移る | 補間した位置 |

遷移:

| 遷移 | 条件 |
|---|---|
| `TRACKING → SUSPECT` | 直近 `suspectWindowMs` に 1ms 未満の更新間隔が 0 個（早期検出が有効なとき） |
| `TRACKING / SUSPECT → HOLD` | `result != Running_OK` または `poseIsValid=false`、または入力が `streamTimeoutMs` 以上止まった |
| `SUSPECT → BLEND` | `result` が OK のまま、1ms 未満の間隔が再び現れた（誤検出だった） |
| `HOLD → PROBATION` | `result == Running_OK` かつ `poseIsValid=true` の入力が来た |
| `PROBATION → HOLD` | 保留期間中に再び OK でない入力が来た（悪いブートストラップ） |
| `PROBATION → BLEND` | OK が `probationMs` 続いた。ただし今回のロスト中に Lighthouse がリセットしなかった（無効なポーズも更新停止もなかった）場合は `shortProbationMs` |
| `BLEND → TRACKING` | `blendMs` 経過 |
| 任意 → `TRACKING`（リセット） | `deviceIsConnected=false`、フィルタ無効化、最大保持時間の超過 |

- 一度も正常に追跡できていない間（電源投入直後など）は、何も保持できないので入力をそのまま流す。

### 保持する位置

- **ロストを検出した瞬間の出力位置**で止める。
- 当初は「光学ロストの推定時刻まで巻き戻す」案だったが、リプレイで却下した。
  手足が動いている最中だと、巻き戻した分（速度 × 最大 250ms）が後ろ向きの段差になる（E4 で最大 37cm）。
  静止しているデバイスでは、巻き戻さなくても検出までのずれは 1cm 未満。

### 座標系

- Lighthouse の driver 座標は、追跡を始めた（ブートストラップした）BS を基準にしていて、別の BS から再開すると原点ごと変わる。
- そのため、保持位置・補間の始点・段差のオフセットはすべて **world 座標**（`qWorldFromDriver` / `vecWorldFromDriverTranslation` を適用した座標）で持ち、
  出力するたびにそのポーズの driver 座標に変換し直す。
- driver 座標のまま保持していた最初の版では、再開時に BS が変わると最大 138cm ずれた（リプレイで発見）。

### 段差リミッタ（`TRACKING` 中の安全網）

- 入力が `TRACKING` / `BLEND` 中に、報告速度で説明できない段差（`stepLimitCm` を超える）を出したら、
  その段差を「オフセット」として受け止め、`stepBlendMs` かけて 0 に減らす（急に跳ばずに滑らかに追いつく）。
- 段差は「前のポーズの位置 + 前のポーズの速度 × 時間差」との差で判定する。時間差は `poseTimeOffset` を含めた実効値で、
  負になる場合（0.1ms 間隔で届いた光学と IMU の更新など）は 0 として扱う。負の時間差を飛ばしていた版では 43cm の段差が素通りした。
- 速い動きの通常の補正は最大 4.7cm（E5 の swing）。既定値は 4.5cm（それ以上の通常補正は滑らかにされるだけで害はない）。

## 出力ポーズの中身

| フィールド | `TRACKING` | `SUSPECT` / `HOLD` / `PROBATION` | `BLEND` | エミッタ（入力停止中） |
|---|---|---|---|---|
| `vecPosition` | 入力 | 保持位置 | 保持位置→入力を smoothstep で補間 | 保持位置 |
| `qRotation` | 入力 | 入力 | 入力 | 最後の入力の回転 |
| `vecVelocity` / `vecAcceleration` | 入力 | **0** | 入力の速度 × 補間率 + 補間による移動速度 / 入力 | **0** |
| `vecAngularVelocity` / `vecAngularAcceleration` | 入力 | 入力 | 入力 | **0** |
| `result` | 入力 | `Running_OK`（設定で入力のままにもできる） | 入力 | `Running_OK` |
| `poseIsValid` | 入力 | `true`（設定） | 入力 | `true`（設定） |
| `poseTimeOffset` | 入力 | 入力 | 入力 | 0 |
| `qWorldFromDriver*` / `qDriverFromHead*` など | 入力 | 入力 | 入力 | 最後の入力 |

- 速度を 0 にするのは必須。SteamVR は速度を使って未来の位置を予測するので、0 にしないと保持しても流れる。
- `BLEND` 中は、出力位置の実際の動きに合った速度を報告する（入力の速度のままだと、予測が補間とずれて段差に見える）。
- world 変換（`qWorldFromDriver*`）は Lighthouse が付けた値をそのまま渡し、位置だけをその座標系に合わせて書き換える。

## エミッタ（更新が止まっている間の補完）

- `HOLD` 中に入力が `streamTimeoutMs`（既定 20ms）以上来なければ、エミッタが `emitHz`（既定 250Hz）で保持ポーズを送る。
- 送り先は、フックが最後に見た `this`（`IVRServerDriverHost` の実体）に対する元の関数（MinHook のトランポリン）。
- 入力が再開したら、エミッタは止まる（入力側が出力を担う）。
- デバイスごとの状態はミューテックスで守る（フックのスレッドとエミッタのスレッドの両方から触るため）。

## 対象デバイスと設定（`steamvr.vrsettings` の `driver_trackingstabilizer`）

| キー | 既定 | 説明 |
|---|---|---|
| `filterEnabled` | `true` | Phase 1 のフィルタ全体のオン/オフ（オフなら Phase 0 と同じ計測のみ） |
| `filterControllers` / `filterTrackers` / `filterHmd` | `true` / `true` / `false` | 対象デバイスのクラス |
| `filterExcludeSerials` | `""` | 対象外にするシリアル（カンマ区切り） |
| `suspectEnabled` | `false` | 更新リズムによる早期検出（リプレイで誤検出の害の方が大きかったため既定は無効） |
| `suspectWindowMs` | `50` | 早期検出の窓 |
| `streamTimeoutMs` | `20` | 入力停止とみなす時間 |
| `probationMs` | `400` | 復帰の保留期間（E2 の悪いブートストラップは OK が 200〜270ms で終わる） |
| `shortProbationMs` | `100` | Lighthouse がリセットしなかった短いロストの後の保留期間（悪いブートストラップはリセット後にしか起きない） |
| `blendMs` | `200` | 復帰時の補間時間 |
| `stepLimitCm` / `stepBlendMs` | `4.5` / `150` | 段差リミッタ |
| `holdReportsValid` | `true` | 保持中を `poseIsValid=true` / `Running_OK` として報告するか |
| `maxHoldSec` | `0`（無制限） | これを超えて保持したら諦めて入力をそのまま流す |
| `emitHz` | `250` | エミッタの送信頻度 |

## リプレイでの検証結果（2026-10-24）

`scripts\replay-all.ps1`（`ots-replay` で Phase 0 の全記録を再生し、`tools/analysis/eval_filter.py` で評価）。既定値で実行。

| 記録 | 基準 | 結果 |
|---|---|---|
| E3（BS 遮蔽）・E5 stomp・各記録の対象外デバイス（正常） | 変化 0.5% 未満 | **0.00%**（全デバイス） |
| E1（静止、電源投入を含む） | — | 1.8〜2.2%（電源投入直後の `Calibrating_OutOfRange` を保持したもの。生の出力の 49cm の段差が 0.6cm に） |
| E2（静止して遮蔽） | 置いた位置からの最大ずれ 2cm 以下 | **0.1〜0.3cm**（生: 最大 84.8cm）。10 番の 4.6cm は布を被せたときに実際に動いた分 |
| E4（体の陰） | 1 フレームの段差 5cm 以下 | **最大 4.1cm**、5cm 超 0 件（生: 最大 43.7cm、5cm 超 49 件） |
| E5（衝撃） | 同上 | **最大 4.7cm**、5cm 超 0 件（生: 最大 6.3cm） |
| E6（移動中の遮蔽） | 高さ・横方向のずれ 3cm 以下 | **高さ 0.6〜2.6cm、横 0.2〜2.8cm**（生: 最大 12.4cm / 12.6cm） |
| 処理時間 | 平均 5µs 未満 | **平均 80ns**（E4 の 72 万回） |

リプレイ中に見つかって直した問題:

1. 保持位置を driver 座標で持っていたため、別の BS から再開すると最大 138cm ずれた → world 座標で持つ。
2. 保持開始時の巻き戻しで、動いている手足が後ろ向きに最大 37cm 跳んだ → 巻き戻しをやめる。
3. 一度も追跡できていない状態からロスト扱いにして、補間で段差を作った → その間は素通し。
4. 段差判定で負の時間差を飛ばし、43cm の段差が素通りした → 0 として扱う。
5. 補間中に入力の速度をそのまま出していたため、速い手で 6cm 程度の段差に見えた → 補間に合った速度を出す。補間中も段差リミッタを効かせる。
6. 早期検出の誤検出が、正常な記録の 0.2〜2% のポーズを止めていた → 既定で無効。

## 要確認事項（既定値の案）

| 項目 | 既定値の案 | 理由 |
|---|---|---|
| 保持中のポーズを「正常」として報告するか | する（`poseIsValid=true`, `Running_OK`） | 無効として報告すると、VRChat などのアプリ側がトラッカーを消したり、別の位置に置き直したりする |
| 最大保持時間 | 無制限 | E4 の腰は 6〜8 秒ロストした。電源断（`deviceIsConnected=false`）では保持を解除する |
| 早期検出（更新リズム） | **無効**（当初案は有効） | リプレイで、正常な記録の 0.2〜2% のポーズを誤検出で止めた（動いている手足が最大 0.3 秒止まる）。ロスト時の効果は無効時と同等だった |
| HMD | 対象外 | 頭の位置を止めると酔いやすい。純正の IMU 推測の方がましな可能性が高い |
| 移動中のロスト | 位置を止める（外挿しない） | E6 で、純正の IMU 推測は進行方向にほぼ止まり、他の方向にずれた。止めた方が誤差が小さい |

## ドライバへの組み込み（実装）

| 部分 | 内容 |
|---|---|
| `driver/src/FilterManager.*` | デバイスごとの `TrackingFilter` とミューテックス、エミッタスレッド（高精度タイマーで `emitHz`）。新しいデバイスは、エミッタスレッドがクラスとシリアルを調べ終わるまで素通し（フックの中ではプロパティを読まない） |
| `driver/src/Hooks.cpp` | フックで入力を記録したあと `FilterManager::Process()` に渡し、出力があればそれを元の関数に渡す。`ForwardPose()` はエミッタ用（元の関数を直接呼ぶ） |
| 記録 | 入力（`Pose`）に加えて、フィルタの出力を `FilteredPose`（記録タイプ 8、エミッタの分は `hookSlot=100`）、状態遷移を `FilterEvent`（タイプ 7）で記録。`python tools\analysis\eval_filter.py <session.otsrec>` で、1 つの記録の入力と出力を比べられる |
| 設定 | `steamvr.vrsettings` の `driver_trackingstabilizer`（上の表）。起動時に読む |
| パイプ | `filter [on\|off]`、`devices`、`config`、`set <key> <value>`（`ots-cli` からも同じ名前で使える）。`set` と `filter` は再起動で設定値に戻る |
| 終了処理 | パイプ停止 → フィルタの切り離し → エミッタ停止 → フック解除（実行中の呼び出しを待つ）→ 記録停止 → フィルタ破棄 |

### オフラインでの確認

- `tests/driver_harness.cpp`: ビルドした DLL を偽の vrserver に読み込ませ、Lighthouse のような入力（光学ロスト → 2 秒でリセット → 1 秒停止 → 5cm 先で再開）を流して確認する。
  結果: HMD は素通し、コントローラーは変化なし、トラッカーは保持中に位置が動かず（速度 0・常に有効）、入力停止中の約 0.94 秒にエミッタが 229 回送信、復帰時の 1 更新あたりの移動は 1cm 未満。
  パイプの `devices` / `set` / `filter on/off` と、終了・アンロードも確認。
- この確認で、パイプのサーバーが 1 クライアントを処理した直後に一瞬受け口がなくなり、続けて来た接続が失敗する問題が見つかった。次の受け口を先に作るように修正した。

### 実機での確認手順（次のステップ）

1. SteamVR を終了して `.\scripts\install-driver.ps1`。
2. SteamVR を起動し、`ots-cli status` で `"filter":"on"`、`ots-cli devices` でコントローラーとトラッカーが `filtered`、HMD が `bypass` になっていることを確認。
3. E2（`ots-cli protocol occlude --target right_hand --record`）と E4（`ots-cli protocol e4 --record`）をもう一度行う。
4. `python tools\analysis\eval_filter.py <記録>` で、入力（純正の出力）とフィルタの出力を比べる。必要なら `ots-cli filter off` で無効にした記録とも比べる。
5. 普段のプレイで 1 時間以上、問題がないか確認する。異常があれば `ots-cli filter off` ですぐ無効にできる（SteamVR の再起動で設定値に戻る）。
